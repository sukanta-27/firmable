Who needs cybersecurity help right now

How one Shodan scan file becomes a ranked list of companies to call: the decisions behind it, how each guess is checked, and what a production version would change.

The appThe code

Numbers come from the full 2026-10-26 scan, run through the pipeline. assumption marks a choice not yet validated; proposal marks something not built.

01The problem

A cybersecurity vendor needs a list of companies with a security problem visible from the internet, plus the evidence a salesperson can open the conversation with. The input is Shodan scan files, hundreds to thousands a month.

17.6 GBone compressed scan file
14.6Mscanner records in it
~19 hof scanning it covers
8,092companies ranked at the end

The work is four steps: find the problem in a scanner reply, score how bad that kind of problem is, attribute the service to a company, and rank the companies.

02What the data showed

  • 6 of 8 open MongoDB replies already showed a ransom note, READ_ME_TO_RECOVER_YOUR_DATA.
  • An open Elasticsearch server listed an index with 1,174,225 documents, no login needed.
  • Open container registries listed repositories called billing and auth-service.
  • 12 of 82 open Ollama AI servers held models named cve-* or pulled from raw IP addresses: someone had already written to them.

The first trap: the records carry 20,988,468 CVE entries, but the scanner tested only 6,111. The rest are looked up from a version string, so a CVE count mostly measures how old the software is.

03The pipeline

A medallion layout: the data is stored in layers, each cleaner and closer to the business question than the last. Each layer is Parquet, partitioned by source file, queried with DuckDB.

  • Rules change far more often than data. Reading the raw file costs 393 s; re-applying every rule costs 47 s. A new rule never re-reads the raw file.
  • Nothing lost or invented. Landing counts lines without the parser, and bronze must match: 14,608,407 rows for 14,608,407 lines.
  • A failed run changes nothing. Each step writes to staging, renamed into place only when every blocking check passes.
  • Reruns replace, never duplicate, because every table is partitioned by the file's SHA-256.
  • Every guess is swappable. Attribution, scoring and ranking are plain functions chosen by name from settings, and every output row records which one made it. That's how two ranking rules run side by side.

04Schema

Each layer has its own grain. Bronze has one row per scanner record. Silver has one row per service, with repeat sightings folded together. Gold has one row per company per ranking rule. In the diagrams, bold column names are keys and join columns.

Bronze: what does each record say?

banner holds every record, typed. vuln holds the record's CVE list, one row per CVE. cve_text holds each CVE's description once.

Bronze: design notes
  • 289 columns in banner: 111 fields copied from the record, 167 protocol objects kept whole as JSON, and 11 that bronze adds.
  • Nothing vanishes. Any key not named elsewhere lands in extra. A line that isn't valid JSON is still a row, with parse_error set.
  • Descriptions are stored once per CVE. Repeated on every record they came to 39.2 GB; stored once, 13.7 MB.

Silver: what exists, who owns it, what does it show?

service is the one deduplicated table. address says who owns each IP. The three logs record every clue to a company name, every finding, and every CVE, one row per sighting. Nothing is scored here.

Silver: design notes and value counts
  • Logs keep every sighting, so a finding seen once survives deduplication. 497,003 services were seen more than once.
  • Keys are built from values: service_key is an md5 of ip, port, transport and hostname, so next month's file gives the same service the same key.
  • Noise is labelled, never deleted. Of 13,670,101 services, 7,460,589 reach the signal rules. The rest answer on more than 50 ports (5,285,023), are CDN edges with no website name (663,757), or are honeypots (260,732).
  • Few addresses belong to the business using them. Only 63,809 of 4,992,440 (1.3%) sit on a company, university or government network.
  • Most name clues are weak. 12,943,735 come from the hostname list, mostly reverse DNS, against 739,925 website names the scanner asked for.

Gold: whose is it, how bad, who goes first?

attribution names a company per service, or none. finding scores each finding. company_finding joins the two for named services and is what a company page reads. company ranks companies, once per ranking rule.

Gold: columns that need explaining
  • confidence and company_key are empty together when no company can be named; a blocking check enforces it. 87.9% of non-noise services are unknown.
  • exploitation_blind is the model's own answer; exploitation_final is after the KEV override.
  • company_score is the worst (or summed) finding score; ranking_score is the same after the confidence weight.
  • company_finding exists for speed: one small table instead of a 1 GB join per request took a company page from 0.20–0.29 s to 0.003 s on a laptop.

05Signals

A signal is something the reply itself shows, never the scanner's guess about it. The rules were derived blind from the bronze tables: 53 candidates, each judged by reading 12 real replies. 14 held as real risk, 20 as potential risk; 5 were unclear and 11 were noise.

Looks like a signalWhy it isn't
A CVE listed on a recordLooked up from the version string. Only scanner-verified CVEs count
The kev flagSays the flaw was exploited somewhere, not on this host
The probe name (darktrack-rat)What the scanner sent, not what answered
The eol-product tagFires on current nginx releases
Self-signed certificates, VPN gatewaysNormal on appliances and remote desktops

The result is 34 exposure types, plus scanner-verified CVEs.

Noise and honeypot filters

Tagged honeypots, addresses answering on more than 50 ports, and CDN edges with no website name never reach a rule. Untagged fakes get filters built from real records. One device MAC address with the same password sat on 13 addresses, so a device password counts only when its MAC appears once. Industrial controllers on busy addresses reported templated ids like Plant_XXXX, so they count only below 10 open ports.

06Attribution: from IP address to business

The hardest part, and the tool's biggest limit. An address is usually registered to a landlord: a hoster, cloud, ISP or CDN. The business renting it is the one worth selling to, and its name is rarely on the record.

Being right comes before catching everyone. A wrong company at the top costs the most, so a service with only weak clues stays unknown, and the unknown count is reported. On synthetic cases, 62 of the 65 services the rules named were right.

Known leak: shared hosting can pass rule A's cut-off, so a few hosters (bluehost.com, godns.net) still appear as companies, ranked 755 to 2,271.

How the rules work

Network type comes from scanner tags, then PeeringDB, where networks state their own type. That covers 71.8% of the records the tags don't. ASdb is used one way only: if it calls a network a landlord, the network can't be the company. Of services with a finding on networks PeeringDB calls "company", 88% sit on networks ASdb calls landlords.

Rule A drops a domain that appears on 10+ addresses on networks it doesn't own, about one service per address: a hoster naming its rented machines. assumption Both cut-offs.

Rule B takes the strongest clue left, first match wins, in the shape Qualys publishes for its own attribution:

ClueConfidence
The website name the scanner asked for (a landlord can't set it)High
The domain a Windows or directory server reports for itselfHigh
Reverse DNSMedium
No name, on the company's own networkMedium
Two or more domains disagreeLow

No hand-made name lists. Every classification comes from a named, dated public source or a rule computed from the data. A list covers only the names in one file, and nobody would keep it current.

07How bad is each finding?

Nobody on the team can judge security severity, so the score needed a benchmark that is consistent and can be checked against outside data. Asking a model for a 1–5 score was rejected: nothing outside can confirm "this is a 4", and the number drifts between runs. Instead, a model answers three factual questions per finding type, and a fixed table turns the answers into a score.

QuestionAnswers
Is this kind of hole being exploited?none · proof of concept · active
Can an attack be automated, with no per-target effort?yes · no
What does an attacker get?information · partial control · total control

The questions are adapted from CISA's SSVC. The two SSVC questions that need knowledge of the company were dropped, a third impact level was added, and the output is a 1–12 score instead of SSVC's four actions, because a ranked list needs finer order.

One outside override: a CVE on CISA's KEV list counts as actively exploited, whatever the model said. One run over all 68 finding types costs $0.02 (Haiku) to about $0.71 (Opus). Gold reads the stored answers and never calls a model, so cost grows with new finding types, not with files.

How the answers were produced
  • One prompt covering all 68 types (34 exposures, 34 vulnerability IDs), each with a plain description and up to 2 real scanner replies.
  • Blind on purpose: no KEV, EPSS, CVSS or counts, since those are what the answers are checked against.
  • Three models: Opus (used for scoring), Sonnet and Haiku as second and third opinions. Opus and Sonnet refused the bare prompt; stating its defensive purpose got both to answer.
  • Strictly validated. An answer outside the allowed values, or "unanswerable", leaves its type unscored, never guessed. Opus answered 66 of 68.
  • The same call writes the one-line explanation a salesperson sees on each finding.

08Who goes first

RuleCompany score
worst_x_confidence_v1 (default)The worst finding's score × that service's confidence weight
sum_x_confidence_v1 (comparison)Every finding's score × its weight, added up

Weights: High 1.0, Medium 0.7, Low 0.4. assumption

  • An attacker needs one hole, and "your worst open door is X" is something a salesperson can say.
  • The score can't double-count one fault reported several ways.
  • It doesn't favour big companies. Rating firms that count findings divide by company size, which the scan doesn't contain.
Ties

636 companies share a score of 9.0, and 2,162 share 6.3. Ties break on confidence, then the number of distinct finding types, then the share of visible services with a finding, then the company key. Related CVEs count as separate types in that second step, so breadth can still reward one fault reported several ways.

Whose service is it?

Checked: 17 synthetic cases, 256 services: 213 right, 40 missed, 3 wrong. Of the 65 services the rules named, 62 were right. Of the 102 that had a real company, 62 were found. ASdb agrees with our network classes on 84.8% of networks.

Can't tell: precision on real data. The cases test the shapes we thought of, and agreeing with ASdb isn't the same as being right.

How bad is a finding?

Checked: Opus's "actively exploited" agrees with CISA's KEV list on 29 of 31 CVEs. FIRST's EPSS rises with its answers: a median of 0.452 for "proof of concept" and 0.999 for "active". Sonnet and Haiku agree with Opus at a chance-corrected kappa of 0.75 to 0.93.

Can't tell: whether the 34 exposure types are judged well. KEV and EPSS cover only CVEs, the three models are all Claude, and they may recall the KEV list rather than judge. The 1–12 table itself is unvalidated. assumption

Who goes first?

Checked: the two rules share only 12 of their top 100. Of 8,676 domains of past ransomware victims (Ransomware.live), 6 match a ranked company. That's an illustration, not a measurement.

Can't tell: whether the order predicts anything. That needs outcomes after the scan.

10Production, and the limits today

DuckDB fit this scope: one file, a 13.2 GB memory peak, about 7.3 minutes on a laptop. Spark is a cluster for a job one machine finishes in minutes. Postgres suits many small writes, and this data is written once per file and then read in bulk.

At hundreds to thousands of files a month proposal

JobTool
Raw files and layersObject storage with Parquet in Iceberg or Delta tables; the same medallion layers
Processing each fileParallel DuckDB workers started by a scheduler, since files never read each other
Gold across months, analysts' questionsA warehouse such as BigQuery, where Censys already ships internet-scan data
App state: users, saved lists, correctionsPostgres
  • "New since last scan," from a service-history table across files: the strongest sales hook.
  • Measured attribution precision: a hand-checked random sample per confidence level, with the measured hit rates replacing the drafted weights.
  • An answer key for severity: CISA's published SSVC answers for the CVEs, and security experts for the exposure types.
  • Outcomes: breach reports and sales results by rank, and leads split at random between two ranking rules.
  • The app: company login (SSO), separate data per customer, revocable sessions, and an audit log of who viewed which company.

Limits today

  • 12.3% of services with an exposure finding can be tied to a company (10,005 of 81,554), and precision on real data isn't measured.
  • Verified CVEs rest on the scanner's own test flag. The reply shows no proof, and the flag is sometimes wrong: the blind analysis found it wrong on at least 14% of BlueKeep records.
  • The score table and confidence weights are unvalidated, and the salesperson line is model-written and unchecked.
  • Many companies tie, so tie-breaks decide much of the order.
  • One file covers about 19 hours, so there's no "new since last time" yet.
The app: API and login

The app reads only the 1.0 MB that pipeline publish writes, baked into the image, so code and data deploy and roll back together. Users are argon2-hashed entries in settings. Sessions are signed HttpOnly cookies. Every /api route sits behind one login check, and 10 failed logins in 15 minutes from one real IP get refused.
